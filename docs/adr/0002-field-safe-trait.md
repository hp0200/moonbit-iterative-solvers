# ADR-2：使用不继承 Ring 的独立 FieldSafe trait 与多重约束

- 状态：已接受
- 日期：2026-11-19

## 背景

迭代求解器需要泛型代数：向量加法、标量乘法等由环约束提供，而预条件与收敛判据还需要安全除法。已核实的事实是：上游不定义算术 trait；`Ring` 来自第三方包 `Luna-Flow/luna-generic`，上游以 `@luna_generic.Ring` 的形式引用。本库同样依赖 `Luna-Flow/luna-generic` 0.4.0。

一个直观设计是声明 `trait FieldSafe : Ring`，让 `FieldSafe` 成为 `Ring` 的子 trait。该设计会把本库能否编译、能否演进押在第三方 `Ring` 是否允许被本库继承这一外部事实上。该事实不可由本库控制，因此不能作为架构前提。

## 决定

- 本库定义独立 trait `FieldSafe`，不继承 `Ring`，也不要求 `Ring` 出现在其父 trait 列表中。
- `FieldSafe` 只提供 `div_safe(Self, Self) -> Option[Self]`：除数为零时返回 `None`，不以 panic 表示失败。
- `FieldSafe` 不重新定义加法、减法或乘法，算术能力仍由 `Ring` 唯一提供。
- 求解器的泛型约束统一写为多重约束 `[T : Ring + FieldSafe]`，其中 `Ring` 指 `@luna_generic.Ring`。
- trait 名使用 `FieldSafe`，不使用 `Field`，避免与未来标准库可能出现的同名抽象冲突。
- 多重约束下所有 trait 方法使用限定语法调用，例如 `Ring::add(x, y)` 与 `FieldSafe::div_safe(a, b)`；点号调用不作为依赖。
- 包内通过私有辅助函数封装限定调用，公开 API 不把语法噪音扩散给下游。

## 依据

- 多重约束只依赖“两个 trait 同时被实现”，不依赖第三方 trait 是否可被继承。外部实现关系的可行性仍可由本库控制。
- `Ring` 与 `FieldSafe` 职责单一：前者提供环算术，后者只提供可失败的除法。这样可以避免形成两套相互竞争的算术抽象。
- `Option[Self]` 把除零从不可恢复的 panic 变为可组合的返回值，符合求解器“数值失效返回错误”的统一语义。
- `FieldSafe` 的命名明确表达“安全除法的字段能力”，同时为未来标准库演进保留命名空间。

## 被否决的替代方案及其代价

### 声明 `trait FieldSafe : Ring`

代价：把本库能否编译建立在第三方 `Ring` 的继承许可上；若上游依赖包的继承规则变化，本库会无端失效。父 trait 约束还会扩大本库协议与第三方协议的耦合面。

### 在 `FieldSafe` 中重新定义加法、减法与乘法

代价：同一值同时受 `Ring` 与 `FieldSafe` 两套算术抽象约束，容易出现方法选择、语义漂移与重复实现；调用方需要在两套方法之间转换，错误处理也会分裂。

### 使用 `Field` 作为 trait 名

代价：与未来标准库抽象重名的风险高，可能导致导入歧义或下游迁移成本；改名会破坏已发布 API。

### 使用可失败的除法运算符或 panic

代价：运算符无法自然表达“可能失败且不 panic”的契约；用 panic 则把数值问题升级为调用方无法局部恢复的控制流失败。求解器的 breakdown 和奇异主元需要可返回、可分类的错误。

### 通过 trait object 隐藏除法差异

代价：本库已选择静态分派以控制泛型单态化与 WebAssembly 产物体积；动态分派会重新引入间接调用和对象生命周期管理，不符合当前设计。

## 后果

- 求解器的泛型签名比继承式字段抽象更长，但可行性只依赖两个 trait 的同时实现。
- 多重约束下必须使用限定语法，点号方法调用不可用；包内辅助函数承担可读性成本。
- 整数类型不实现 `FieldSafe`，从 trait 实现层拒绝整数求解器实例化。
- 若未来标准库提供兼容的安全除法抽象，应由新的 ADR 决定迁移，而不是在本 ADR 中预先耦合。
