# ADR-1：求解器以包级函数暴露，不包装上游矩阵

- 状态：已接受
- 日期：2026-11-19

## 背景

本库的求解算法作用于 `hp0200/moonbit-sparse-math` 提供的稀疏矩阵与向量数据。一个自然但不可行的设想是：为本库定义上游矩阵的包装类型，再把 `solve` 一类方法挂到包装类型上。

MoonBit 规定方法只能与类型定义在同一包内，外部包不能给外部类型添加公开方法。上游类型定义在上游包，因此本库无法合法地为其增加公开的求解方法。

## 决定

- 不定义上游矩阵的包装类型。
- 求解器以本库包的公开函数暴露，例如 `cg_solve`。
- 函数直接接收上游公开类型或本库算法所需的参数，不引入重复的矩阵所有权类型。
- 公开 API 保持位置参数风格，与上游既有风格一致。
- 求解结果显式携带成功解或数值错误，不依赖抛出或 panic。

```text
// 签名示意，非最终代码
cg_solve(matrix, rhs, initial_guess, tolerance, max_iter, preconditioner)
    -> result carrying either the solution or a numerical error
```

## 依据

- MoonBit 的包级方法归属规则使“外部类型 + 本库方法”的包装方案成为唯一可选的方法式 API；而该方案会引入不必要的类型转换层。
- 上游已定义稀疏矩阵与向量的数据所有权。新增包装类型会产生两套近似等价的类型身份，增加调用方在上下游 API 之间转换的负担。
- 包级函数可以直接表达“算法作用于既有数据”，同时避免本库对上游存储布局作出额外承诺。
- 稀疏存储不是本库职责，包装类型容易让边界重新滑向存储层实现。

## 被否决的替代方案及其代价

### 包装类型 + 方法

代价：需要定义并维护新的矩阵/向量包装类型；每次调用上下游能力都要转换；两个类型身份可能造成泛型约束、诊断结果和错误处理不一致；调用方容易误以为包装类型拥有存储或修改语义。

### 在 `impl` 或 `extend` 中提供方法式语法

代价：外部类型的方法公开能力受包边界限制；即便在本包内能获得某种点号语法，下游也只能限定调用，无法形成稳定的公开方法契约。把这类语法作为主 API 会制造“本包可用、下游不可用”的不一致。

### 将求解器贡献到上游仓库

代价：使上游承担求解算法职责，破坏“上游提供存储与诊断、本库专注算法”的边界，也让当前独立新库无法按自己的版本节奏发布。

### 仅暴露宏或代码生成入口

代价：API 可发现性差，错误处理与泛型约束难以在生成层保持一致，调用方也无法直接按普通包函数理解与组合求解流程。

## 后果

- 公开入口采用稳定的包级命名，例如 `cg_solve`，文档按包组织。
- 调用方不能使用矩阵对象上的点号求解语法，需要通过包名或导入限定调用。
- 本库不拥有矩阵生命周期，也不承诺替代上游的诊断或存储 API。
